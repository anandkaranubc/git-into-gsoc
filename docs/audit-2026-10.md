# Audit record, October 2026

An end-to-end audit of the project ran on 2026-10-20 and 2026-10-21. This page lists every weakness it found and the pull request that resolved it, so the reasoning behind the current design is not lost. Pull request numbers refer to [the repository on GitHub](https://github.com/anandkaranubc/git-into-gsoc/pulls?q=is%3Apr+is%3Amerged).

## Discovery

| Finding | Resolution |
|---|---|
| Issue search required both "good first issue" and "help wanted" on the same issue and used a repository-only qualifier, so it returned almost nothing | #10 rewrote the query, scoped it to GSoC organizations by default, and verified the top candidates against their timelines (claims, linked pull requests, approvals, contested threads) |
| No way to tell which of an organization's repositories mentors actually work in | #11 added `repos`, ranking by ideas-page mentions and open beginner issues |
| Organization search downloaded a 15 MB archive on every run and failed offline | #18 embedded a compact snapshot and made the archive lazy; cold search dropped from 3.8s to 0.9s |
| Ideas pages were unreadable as lists; mentors and umbrella pages were invisible | #27, #31, #50, #57 added `ideas`, `mentors`, umbrella-page following, and reserved-label signals |

## Repository health

| Finding | Resolution |
|---|---|
| Health probed six file paths one by one, counted bot pull requests, rewarded stars, and reported a "first-time contributors" number that GitHub makes always zero | #11 switched to the community profile; #22 replaced the newcomer count with distinct outside authors merged, required a real sample for the outside merge rate, and removed star points |
| Outside contributors were defined by `author_association`, which counts maintainers as outsiders | #29 read assignable users over GraphQL; #54 read the public assignees endpoint so the no-token path has the same insider set |
| No signal for how quickly humans reply to newcomers | #29 measured the first human reply from pull request timelines (token); #56 derived it from recent repository comments (no token), reported with its sample size; #61 widens that comment window on busy repositories until the figure rests on at least five pull requests |
| No token-free evidence that newcomers get through | #33 counted single-commit authors and bus factor from commits.ecosyste.ms |

## Journey and guidance

| Finding | Resolution |
|---|---|
| Phases had no onboarding, no daily driver, and no structured notes | #27 added `profile`, `next`, and `log`; #21 added `--track` and `--shortlist` |
| Community contact came after claiming an issue, contrary to the official contributor guide | #22 moved `community` before `find_issues`; #34 added `orient` and `iterate`, with migration of saved progress |
| The proposal step was a static checklist | #21 added an evidence-based proposal check (verified contribution links, timeline detail, specificity, placeholders, copied ideas-page text); #27 added drafts and contribution evidence |

## Installation and platforms

| Finding | Resolution |
|---|---|
| A Bash-only installer that needed a clone and hand-pasted JSON; nothing for Windows | #14 added `setup`, shipped the skill in the wheel, rewrote `install.sh` for clone-or-curl use, and added `install.ps1`; CI runs on macOS and Windows |
| `setup` with a redirected home still ran `claude mcp add` against the real config | #29 skips assistant CLIs for a redirected home |
| Plugin, extension, and registry routes existed but were undocumented for beginners | #51 added them to the assistant guide |

## Reliability, security, performance

| Finding | Resolution |
|---|---|
| Empty progress values were saved and unknown phases crashed | #16 |
| Rate-limit errors named the hourly limit when the search limit was the cause | #48 |
| Cache and progress files were world-readable; two defaults ignored the configured target year | #43 |
| MCP results were pretty-printed and sent twice; tools had no titles, annotations, or error channel | #21, #26 |
| Twenty-five commands in one flat help list; no way to see which data source was down | #45 |

## Documentation and process

| Finding | Resolution |
|---|---|
| Docs described the first prototype | #12 rebuilt the beginner guide; #13, #23, #24 rewrote the skill and user-facing strings; #41 placed every new command at the step where it is needed |
| No release process, features bumping only the patch version, no automated assets | #36 set the policy and wrote the releasing guide; #38, #44, #47 attached bundles, wheels, and source archives to every release and published the MCP registry entry automatically |
| Coverage gate at 50 percent | #21 raised it to 65 percent; coverage stands at 86 percent with 267 tests |
| `org` failed outright when the project archive was down although the profile comes from the embedded snapshot | #61 made project titles optional detail; found by a scripted consistency sweep of commands, tools, settings, and phases against the docs and skill |

## Outside the repository

Publishing to PyPI needs a trusted publisher record on the PyPI account that owns the project name. The workflow, the GitHub environment, the installers' PyPI-first fallback, and the exact values to enter are all in place; see [Releasing](releasing.md). Until that record exists, the one-line installers use the Git URL, which the audit verified works on all three platforms.
